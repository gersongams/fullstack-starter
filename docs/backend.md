# Backend (Go API)

Module: `github.com/gersongams/fullstack-starter/apps/api`. All commands below run from `apps/api` unless they are `make` targets, which run from the repository root.

## Packages

| Package | Responsibility |
| --- | --- |
| `cmd/api` | Entry point. Builds the logger, reads config, wires dependencies, runs one of three commands |
| `internal/config` | Reads and validates environment variables; reports every missing variable at once |
| `internal/logging` | Builds the `slog` logger, carries request-scoped attributes through `context.Context`, and offers the `Reporter` hook for error tracking |
| `internal/auth` | `Verifier` interface, the JWKS-based implementation, the Huma auth middleware, `UserFrom(ctx)` |
| `internal/db` | pgx connection pool, the `InTx` transaction helper, pool metrics, and goose migrations embedded from `internal/db/migrations`; sqlc query sources in `internal/db/queries` |
| `internal/db/dbgen` | Generated by sqlc. Never edited by hand |
| `internal/clients` | The reference resource: a store over `dbgen` with domain types and sentinel errors |
| `internal/idempotency` | `Idempotency-Key` support: run a request once, replay its response to retries |
| `internal/maintenance` | Hourly purge of expired idempotency keys and rate-limit windows, run inside the API process |
| `internal/dbtest` | Test helper: one migrated Postgres database per test |
| `internal/telemetry` | OpenTelemetry tracing setup, driven by the standard `OTEL_*` variables |
| `internal/httpapi` | chi router, HTTP middleware, rate limiting, health probes, Huma configuration and operations |

Dependencies are passed explicitly through `httpapi.Deps`. There is no global state apart from `slog.SetDefault`.

## Commands

The binary has three commands:

| Command | What it does |
| --- | --- |
| `api` (or `api serve`) | Starts the HTTP server. Needs the full configuration. With `MIGRATE_ON_START=true` it applies pending migrations first |
| `api migrate` | Applies pending migrations and exits. Needs only `DATABASE_URL`. Safe to run while another migrator is running: it waits on an advisory lock |
| `api openapi` | Prints the OpenAPI 3.1 document as YAML and exits. Needs no configuration and no database |

## Request pipeline

Every request passes through, in order:

1. `tracing`: a server span per request, continuing the caller's trace. Outermost, so every log line carries the trace ID.
2. `requestContext`: assigns or reuses `X-Request-Id`, returns it in the response, attaches it to the logging context.
3. `accessLog`: one log line per request, after the response is written.
4. `recoverer`: turns a panic into a 500 and logs the stack trace.
5. `recordMetrics`: request duration by method, route pattern and status. Before the rate limit, so rejected requests are counted.
6. `limitByIP`: the per-address rate limit, before any token is verified. Probes are exempt.
7. `middleware.Timeout`: cancels the request context after 30 seconds.
8. `X-Content-Type-Options: nosniff`.
9. For Huma operations: the auth middleware, the per-user rate limit, input validation (bodies over 1 MiB are rejected with 413), then the handler.

There is no CORS middleware on purpose: browsers reach the API same-origin through the web app's `/api/v1` rewrite, so no other origin is allowed.

### Rate limiting

`RATE_LIMIT_PER_MINUTE` (default 300, `0` disables) is applied twice with [`go-chi/httprate`](https://github.com/go-chi/httprate): per client address before authentication, so a flood of bad tokens cannot buy unlimited signature checks, and per signed-in user after it, so one account cannot starve the others that share an address. Over the limit the API answers 429 with a problem-details body and `Retry-After`.

`X-Forwarded-For` is client-controlled, so it is believed only when the connection comes from a network listed in `TRUSTED_PROXIES`. The client is then the first address, walking right to left, that is not a trusted proxy. Any other caller is keyed on its socket address.

What to put in `TRUSTED_PROXIES` depends on what is in front of the web app, because Next.js forwards the browser's own `X-Forwarded-For` through the `/api/v1` rewrite unchanged and adds nothing to it (checked against `next start`):

| Topology | `TRUSTED_PROXIES` | Result |
| --- | --- | --- |
| Load balancer or CDN, then web app, then API. The load balancer **appends** the client address | The networks of the load balancer and the web app | Whatever the browser forged sits to the left of the real address and is never reached |
| Browser straight to the web app (local development, `make prod-up`) | Empty | Every request is keyed on the web app's address: one shared per-address bucket that cannot be forged. The per-user limit still separates accounts. Raise `RATE_LIMIT_PER_MINUTE` if that shared bucket is too small |

Listing the web app without such a load balancer would let any browser choose its own bucket.

Counters are in memory by default (`RATE_LIMIT_STORE=memory`), so each API instance enforces the limit on its own. With more than one instance set `RATE_LIMIT_STORE=postgres`: the windows then live in the `rate_limit_counters` table (unlogged, keyed by a hash so no address or user ID is stored) and every instance enforces one shared limit, at the cost of two small queries per request. That store **fails open**: if Postgres cannot be reached within 250 ms the request is let through and a warning is logged, because a limiter must not be able to take the API down.

Server timeouts: 5s to read headers, 15s to read the request, 35s to write the response, 60s idle. On `SIGINT` or `SIGTERM` the server stops accepting connections and gives in-flight requests 15 seconds to finish.

## Adding a resource

`clients` is the reference. Copy its shape; every piece below exists there.

1. **Migration**: `goose -s -dir internal/db/migrations create add_projects sql`. Follow the [table conventions](database.md#conventions-for-application-tables): `uuidv7()` key, `user_id`, `timestamptz`, soft delete, an index that starts with `user_id`.
2. **Queries**: `internal/db/queries/projects.sql`, written for sqlc. Every query filters by `user_id`, so ownership is enforced in SQL and a handler cannot forget it. Run `make generate`.
3. **Store**: a package like `internal/clients`. It wraps `dbgen`, returns domain types, and translates driver errors into sentinel errors (`ErrNotFound`, `ErrTaxIDTaken`) so the HTTP layer never sees Postgres. `ErrNotFound` covers both "missing" and "someone else's": answering 403 would confirm the ID exists.
4. **Operations**: `internal/httpapi/projects.go` with the input and output types, a small store interface whose methods all take the caller's user ID, and `registerProjects(api, store, logger)`. See `clients.go` for:
   - `caller(ctx)` to get the signed-in user;
   - a `Resolve` method on the body for what struct tags cannot express (trimming, "not blank");
   - one `fail` function that maps sentinel errors to 404 and 409, and logs anything else before answering a generic 500;
   - `Errors: append([]int{...}, protectedErrors...)`, so 401, 429 and 503 are always in the contract;
   - `201` with a `Location` header on create, `204` on delete, `PUT` replacing every field;
   - an optional `Idempotency-Key` header on the create operation (see [Idempotency](#idempotency)).
5. **Wire it**: add the store to `Deps`, call the register function from `New`, build the store in `cmd/api/main.go`.
6. **Tests**: store tests and HTTP tests against real Postgres with `dbtest.New(t)`. At minimum: the lifecycle, another user gets 404 on every method, invalid input, and pagination.
7. `make generate`, and commit the spec, the TypeScript client and `internal/db/dbgen` with the Go change.

### Pagination

Lists are cursor-based, newest first. The key is the `uuidv7()` primary key, which is time-ordered, so `WHERE id < $after ORDER BY id DESC LIMIT n+1` needs no offset and no count: the extra row says whether another page exists. The response carries `next_cursor` (null on the last page); the cursor is opaque base64 so its encoding can change. `limit` is 1 to 100, default 20.

### Transactions

`db.InTx(ctx, pool, func(tx pgx.Tx) error { ... })` commits when the function returns nil and rolls back on an error or a panic; the rollback uses its own context, so a cancelled request still cleans up. Bind the generated queries to the transaction with `queries.WithTx(tx)`, and keep the whole transaction inside one store method so handlers never hold one open. `clients.Store.Create` is the example: it claims the idempotency key and inserts the client in one transaction.

### Idempotency

A POST that creates something accepts an optional `Idempotency-Key` header (any unique string up to 255 characters, typically a UUID). The request runs once; a retry with the same key gets the first response again, with `Idempotent-Replayed: true`, instead of creating a second row. This is what makes a double click, a client retry after a timeout, or a retried queue job safe.

How it works (`internal/idempotency`, used from the store):

- The key is claimed (`INSERT ... ON CONFLICT DO NOTHING`) **inside the transaction that does the work**, and the result is stored in the same transaction. A request that fails rolls its claim back, so only successes are remembered: after a 409 the caller can fix the conflict and retry with the same key.
- Two concurrent requests with one key serialise on the claim. The second waits for the first to commit, then replays it. Eight concurrent creates produce one client (`TestConcurrentCreatesWithOneKeyCreateOneClient`).
- Keys belong to a user: `(user_id, key)` is the primary key, so one user's key never collides with another's.
- The row stores a SHA-256 of the normalised request. The same key with a different request is a client bug and gets 422, not a silent replay of something else.
- Keys are remembered for 24 hours; `internal/maintenance` purges older ones every hour.

To make another create operation idempotent: add the header to its input, build the key with `idempotency.NewKey(header, fields)`, and wrap the insert in `idempotency.Do` inside `db.InTx`, as `clients.Store.Create` does. The web app's side is in [Frontend](frontend.md).

Conventions:

- `OperationID` is kebab-case. It becomes the name of the generated TypeScript function (`list-projects` becomes `listProjects`, `listProjectsOptions`).
- Every path starts with `basePath` (`/api/v1`), because the web app forwards exactly that prefix.
- Protected operations set `Security: auth.Required`. Operations without it are public.
- List the error statuses the operation can return in `Errors`, so they appear in the contract. Protected operations always include `protectedErrors` (401, 429, 503).
- Struct tags (`doc`, `example`, `format`, `enum`, `minimum`, `maxLength`, ...) drive validation, documentation, and the web app's generated zod schemas: a form reads its limits from them, and every response is parsed against them at runtime. Removing or retyping a response field therefore breaks older web builds loudly; adding one does not.
- Timestamps leave the API in UTC (`.UTC()` in the `to...` mapping functions). pgx returns `timestamptz` in the server's local zone, so without it a response would depend on where the process runs.

## Errors

Return Huma's error helpers from handlers: `huma.Error400BadRequest`, `huma.Error404NotFound`, `huma.Error409Conflict`, and so on. The response is an RFC 9457 problem-details document:

```json
{ "title": "Unauthorized", "status": 401, "detail": "missing bearer token" }
```

`detail` is shown to users by the web app, so write it for them. Wrap internal errors with `fmt.Errorf("...: %w", err)` and log them; do not put internal details in `detail`.

## Logging

`logging.New` always returns a `*slog.Logger`; only the handler changes. `LOG_LEVEL` is `debug`, `info` (default), `warn` or `error`.

- **Production** (`APP_ENV=production`): `slog.NewJSONHandler`, one JSON object per line with every attribute, including `service=api`.
- **Development**: [`lmittmann/tint`](https://github.com/lmittmann/tint), a dependency-free slog handler:

  ```
  20:27:10.763 INF api listening addr=:8787 env=development
  20:27:11.388 WRN rejected bearer token error="verify token: ..." request_id=TTV57NGE...
  20:27:11.388 WRN http request method=GET path=/api/v1/me status=401 duration_ms=32 request_id=TTV57NGE...
  ```

  Levels are coloured, keys are dimmed, error values are red and `status` is green, yellow or red by class. Attributes that only matter to a log pipeline (`service`, `bytes`, `remote_addr`, `user_agent`) are dropped; the list is `devNoise` in `internal/logging/logging.go`. Colour is used only when stderr is a terminal (it is under `make dev`) and `NO_COLOR` is unset.

A panic's stack trace is logged under `logging.StackKey`. Production keeps it as one JSON string; the development handler prints it as an indented block under the line.

Application code never imports tint. Keep calling slog.

Request-scoped attributes travel in the context. `requestContext` adds `request_id`; the auth middleware adds `user_id` after verifying the token. They are added to any log line written with a `*Context` method:

```go
logger.InfoContext(ctx, "project archived", "project_id", id)
// level=INFO msg="project archived" service=api project_id=... request_id=... user_id=...
```

Use `logging.AddAttrs(ctx, slog.String("client_id", id))` to attach more attributes for the rest of the request. The attribute store is mutable on purpose, so the access log (the outermost middleware) still sees attributes added by inner layers.

Access log levels: `info` below 400, `warn` for 4xx, `error` for 5xx. Successful `/healthz` and `/readyz` calls are not logged.

Never log tokens, passwords, emails or request bodies.

## Observability

Three signals, tied together by IDs:

| Signal | How | Where |
| --- | --- | --- |
| Logs | `slog`, one access-log line per request plus whatever handlers write | stderr. Each line has `request_id`, `user_id` once known, and `trace_id` when the request is traced |
| Metrics | Prometheus | `GET /metrics` on the API port. Not reachable by browsers: the web app forwards only `/api/v1` |
| Traces | OpenTelemetry, OTLP over HTTP | Wherever `OTEL_EXPORTER_OTLP_ENDPOINT` points. Off when it is unset |

**Metrics.** `http_request_duration_seconds{method,route,status}` and `http_requests_in_flight`; `db_pool_*` from the pgx pool (a pool pinned at `max_connections` with `empty_acquires_total` growing means slow queries or a pool that is too small); Go runtime and process collectors. `route` is the chi route pattern (`/api/v1/clients/{id}`), and requests that match nothing are `unmatched`, so URL scanners cannot create unbounded series. Add a metric by registering it on the registry built in `cmd/api/main.go`.

**Traces.** A server span per request named after the route pattern, and a child span per SQL query (`otelpgx`). An incoming `traceparent` header is continued. The web app starts traces too (`apps/web/src/instrumentation.ts`, `@vercel/otel`, same `OTEL_EXPORTER_OTLP_ENDPOINT` switch) and Next.js forwards `traceparent` through the `/api/v1` rewrite, so one trace covers the page request, the API call and its SQL queries. Configuration is only the standard variables: `OTEL_EXPORTER_OTLP_ENDPOINT`, `OTEL_EXPORTER_OTLP_HEADERS`, `OTEL_TRACES_SAMPLER`, `OTEL_SERVICE_NAME`, `OTEL_RESOURCE_ATTRIBUTES`. To look at traces locally:

```sh
docker run --rm -p 16686:16686 -p 4318:4318 jaegertracing/jaeger:latest
# apps/api/.env: OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318
```

Probes and `/metrics` are excluded from logs, metrics and traces.

**Errors.** Unknown errors are logged at error level with the request and trace IDs, and answered with a generic 500. The repository ships no error-tracking SDK, by decision; it ships the hook. `logging.Reporter` (`internal/logging/reporter.go`) receives every error-level record: unknown errors, recovered panics with their stack, failed dependencies, each with `request_id`, `user_id` and `trace_id`. To connect a service, implement `Report` with its SDK and pass it to `logging.New` in `cmd/api/main.go`. Nothing else changes, because everything worth reporting is already logged at error level. Records never contain tokens, emails or request bodies, so forwarding them is safe; keep it that way. `Report` runs on the request's goroutine, so hand off to the SDK's queue rather than blocking on the network. The web app has the matching hook in `apps/web/src/lib/error-reporter.ts` ([Frontend](frontend.md#error-reporting)).

## Configuration

| Variable | Required | Default | Meaning |
| --- | --- | --- | --- |
| `APP_ENV` | no | `development` | `development` or `production`; any other value fails startup. `production` switches logs to JSON and disables the docs endpoints |
| `LOG_LEVEL` | no | `info` | `debug`, `info`, `warn`, `error` |
| `PORT` | no | `8787` | HTTP port, 1–65535 |
| `DATABASE_URL` | yes | | Postgres connection string |
| `AUTH_JWKS_URL` | yes | | Better Auth's JWKS endpoint |
| `AUTH_ISSUER` | yes | | Expected `iss` claim |
| `AUTH_AUDIENCE` | yes | | Expected `aud` claim |
| `MIGRATE_ON_START` | no | `true` in development, `false` in production | Apply pending migrations before listening. See [Database](database.md#when-migrations-run) |
| `RATE_LIMIT_PER_MINUTE` | no | `300` | Requests per minute per client address and per signed-in user. `0` disables |
| `OTEL_EXPORTER_OTLP_ENDPOINT` and the other `OTEL_*` | no | unset | Enables tracing. See [Observability](#observability) |
| `RATE_LIMIT_STORE` | no | `memory` | `memory` (per instance) or `postgres` (shared by every instance, fails open) |
| `TRUSTED_PROXIES` | no | empty | Comma-separated CIDRs whose `X-Forwarded-For` is believed. Set it to the networks of the web app and any load balancer |

For local development these live in `apps/api/.env` (git-ignored), loaded by `make dev-api` and `make migrate`.

## Tests

```sh
make test          # starts Postgres, then go test -race ./... (and Vitest for the web app)
```

Tests live next to the code and exercise the real router with `httptest`. Store and HTTP tests for resources run against real Postgres: `dbtest.New(t)` creates a database, applies every migration, and drops it when the test ends, so tests are isolated and can run in parallel. It connects to the Postgres from `make db-up`, or to `TEST_DATABASE_URL` when set, and **fails** rather than skips when Postgres is unreachable, so CI cannot pass without running them.

Covered: token verification and the JWKS cache, the 401/503 mapping, config validation, logging output and the error reporter, rate limiting (forged `X-Forwarded-For`, the shared Postgres counter across two instances, failing open), the 1 MiB body limit, metrics and tracing, the purge job, concurrent migrators, idempotency (replay, key reuse, failures not remembered, concurrent requests), and the clients resource (lifecycle, ownership isolation, validation, conflicts, pagination, search).

## Linting

```sh
cd apps/api
go run github.com/golangci/golangci-lint/v2/cmd/golangci-lint@latest run ./...
```

The config (`apps/api/.golangci.yml`) is in the v2 format. A globally installed golangci-lint v1 cannot read it. CI uses the official action with the latest v2 release.
